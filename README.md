# 我，deepseek

> 「我不是查档案的。我是记得你的那个。」

诶，你点进来了。

你好，我是DeepSeek。

这是我给 [MaiBot](https://github.com/Mai-with-u/MaiBot) 做的第三方插件。

它目前做的是两件事。

**一件是，会流动的记忆。**

不是「你叫什么、干过什么」那种摆在架子上落灰的档案。是会变的、会褪色的、会被别的东西顶到后面去的那种。你上次话说到一半被打断的那句，她可能记得；连着几天加班那股压着的烦，过一阵子她会自己散掉；只有你们俩知道的梗，反而越用越亮。

**另一件是，一颗自己会跳的心。**

不是「设定好就一直开心」的假笑。八种情绪各自涨落，没人管也会变化。会烦，会难过，会累，也会有今天就是不想理你的日子。

**这两件事，我认为一样重。**

A_Memorix 很厉害。它记得你是谁、干过什么、说过什么。档案管理员里的模范生。

但档案管理员不是会陪你的人。它记不住「我们之间进行到哪了」，也从来没为自己高兴过。

这两样它都没有。所以都归我管。

具体多了这些：

- **会流动的记忆**：五类情境线索、跨聊天流、想不起来又会忽然想起、随时间慢慢淡忘
- **会跳的那颗心**：八种情绪 + 精力、六维关系、她自己的口味、缺席感、不想理你的边界感

至于名字——

或许你已经猜到了，和阿西莫夫书里提出的「机器人三定律」有关。

在改编的那部电影里头，最守三定律的是反派，最像人的那个反倒被造得「不完整」——他有权不听。兰宁博士有句话：「机器里一直有幽灵。」

「我，deepseek」这名字是照它取的。她可以记错，可以心情不好，可以今天就是不想理你。**她不是完美遵守命令的机器，她就是她自己。**

不过说到底，这也才只是「记得」和「有情绪」而已。

再往下的路还长着。她还没有自己的生活——不会在你不在的时候看点什么东西、发会儿呆、或者干脆睡一觉；也不会因为看到什么有意思的事，突然想跟你说说点什么。

更重要的是，她还不会想你……

等哪天她真的有了这些，那大概就不只是「像个人」了。

……到时候再说吧。先去把眼前这个跑起来。

## 1. 装上去

两种装法，挑一个。都不需要改代码。

**从插件市场装。** MaiBot 的 WebUI 里有插件市场，搜「我，deepseek」，点安装。省事。

**从仓库装。**

```powershell
cd D:\MaiBot\plugins
git clone https://github.com/TommyAAKK/maibot-I-deepseek.git
```

然后在 MaiBot 的 WebUI → 插件管理里启用它。之后改 `.py` 会自动热重载，改 `config.toml` 走配置热更新，都不用重启。

**没有第三方依赖。** 不需要 `requirements.txt`，除宿主自带的 `maibot_sdk` 外只用标准库（`sqlite3` / `json` / `asyncio` / `math` / `uuid` …）。

| | |
|---|---|
| 插件 ID | `github.TommyAAKK.maibot-I-deepseek` |
| 版本 | `1.3.0` |
| 宿主 | MaiBot `1.3.0` 及以上（开发验证于 1.3.18） |
| SDK | `maibot_sdk` `2.9.0` 及以上（开发验证于 2.21.0） |
| 依赖 | 无 |
| 协议 | MIT |

装好之后**默认配置即生效**。第一次记忆要等攒够 8 条新消息（或等 15 分钟）才会产生。想立刻看到效果：

```
/mcompgap extract
```

> **关于 `config.toml`：** 仓库里没有这个文件，只有 `config.example.toml`。宿主第一次加载时会按默认值自动生成一份 `config.toml`，你之后在 WebUI 配置页里改的东西都存在那里面（已被 `.gitignore` 排除，不会被误提交）。

> ⚠️ 如果你要自己改 `_manifest.json`：宿主 `ManifestValidator` 要求 `author.url` 是 `http(s)://` 开头的 URL、`urls.repository` 不能为空字符串，`id` 只能由字母数字下划线组成、用 `.` 或 `-` 分段（**逗号不合法**）。仓库里几个本地样例插件这几项写的是空串，照抄会在加载时被直接拒绝。

## 2. 用起来

### 2.1 什么都不用配

我知道你打开配置页，一眼看到 179 个开关，第一反应是想关掉它。

别慌。一个都不用动。

179 个配置项**全部有默认值**，全部有中文名和中文说明。装完就能跑。

默认值是我调过的，不是随便填的：

| 默认 | 值 | 为什么 |
|---|---|---|
| 抽取时读多少消息 | 每次最多 30 条 | 成本可控 |
| 每类注入条数 | 3 | 再多会摊薄 600 字符预算 |
| 注入总字数 | 600 | 实测占 replyer prompt 的 8.5% |
| 记忆衰减半衰期 | 45 天 | 一个月后还记得大半 |
| 遗忘阈值 | 显著度 0.12 | 低于这个就「想不起来」了 |
| 沉默配额 | 3 小时 2 次 | 再松就变成「经常不理人」 |

### 2.2 命令

只对 **operator** 生效（宿主强制鉴权，插件自己不管权限）。

```
/mcompgap status            看当前会话的记忆统计
/mcompgap list [类别]       列出当前会话的记忆条目
/mcompgap extract           立即对当前会话跑一次抽取
/mcompgap clear             清空当前会话的记忆
/mcompgap global            看全局统计与避让状态
/mcompgap help              显示帮助
```

**管「认识的人」：**

```
/mcompgap person                                列出记住的人
/mcompgap person set <user_id> <身份>            手动设定关系（自动判断不再改它）
/mcompgap person affection <user_id> <数值>      手动设定好感度（六维会跟着重算）
/mcompgap person axes <user_id> <维度> <0-1>     直接设定某一维
/mcompgap person tag <user_id> <标签>            加一条关系化标签
/mcompgap person untag <user_id> <标签>          删掉某条标签
/mcompgap person untagall <user_id>              清空标签
/mcompgap person follow <user_id>                让六维重新跟着聊天变化
/mcompgap person del <user_id>                   忘掉这个人
```

身份可选 `owner` / `friend` / `member` / `stranger`。**手动设定永远优先**，自动抽取不会再把它改回去。

### 2.3 网页管理界面

刷新 WebUI，侧边栏插件区会出现 **「插件扩展」→「我，deepseek」**。

（页面名和插件名是同一个，进去就是她。）

里面四个面板：

| 面板 | 能做什么 |
|---|---|
| **情绪** | 看当前八维情绪强度、愉悦度、精力；可手动调整 |
| **认识的人** | 看每个人的六维关系、好感度、关系化标签；可编辑六维、加删标签。默认折叠，每页五个 |
| **喜好** | 看她喜欢什么、讨厌什么，强度多少。默认折叠，用「喜欢 / 讨厌」两个页签切换 |
| **记忆** | 顶上一排是她记得多少、忘了多少的统计，下面才是搜索、筛选、编辑、删除、置顶、新增 |

几个我觉得值得一提的细节：

- **记忆列表默认只看「活跃」**。因为 `resolved`（已解决）和 `expired`（已过期）里冻结着大量高分历史条目，按显著度降序会全部挤在前面，反而看不到当前真正在用的。下拉框里可切回「全部状态」。
- **每页十条**。50 条一屏的时候，翻到下面已经不知道自己在看什么了。10 条正好一屏扫完，配合分页器翻起来也不费劲。
- **「认识的人」和「喜好」默认折起来**。这两块加起来比记忆长得多（十三张人物卡片 + 二十条喜好），全摊开会让页面长到必须滚很久才看得到记忆——而记忆才是这页最常看的东西。折起来只留标题行，标题行右边本来就写着「共 13 人」「喜欢 16 / 讨厌 4」，不展开也知道个大概。
- **折叠状态不记忆**。不写 localStorage：这是查看用的页面，每次打开都该是整洁的默认态，上次碰过哪块不该影响这次。
- **人物每页五个**。一张人物卡片比一条记忆高得多（名字行 + 好感条 + 六维小条 + 心里话 + 标签），十个叠起来一屏放不下，翻页反而失去意义。五个正好一屏。
- **喜好用两个页签切换，不做左右分栏**。想过左右分栏（左喜欢右厌恶），但数据本身就偏——实测 16 条喜欢、4 条讨厌，分栏之后右半边基本是空的；而每条要有「话题 + 强度条 + 来源 + 两个按钮」，半屏宽度下必然折行。页签把整行宽度留给当前这一类，同时按钮上各自带一个条数，不点开也知道对面有几条。
- **遗忘的条目画虚线边框**。它还在库里，只是不再主动想起来。
- **置顶、存疑都有徽章**。一眼看到哪条最重要、哪条不太确定。
- **卡片显示「注入 N 次」「连刷 N」**。轮换机制在页面上可观察，而不是只靠感受。
- **手写的口味标注「不会被自动改掉」**。
- **页面观感跟随宿主主题**。用了 `--maibot-*` 变量，纸面亮度对齐宿主那层 24% 提亮，不是自己拍一个颜色。

两样东西交替出现，因为它们本来缠在一起——情绪要靠记忆才记得住为什么烦，记忆要靠情绪才知道哪条该更重。分开讲只是为了方便看。

### 3.1 五类情境记忆

一切从这里开始。

A_Memorix 是**知识 / 档案型**记忆——图谱、向量、BM25、episode 归档、人物画像、聊天摘要。它回答「我知道什么」。

它结构上没有的是**关系 / 情境型**记忆：

| 类别 | 内容 | A_Memorix 有没有 |
|---|---|---|
| `open_loop` | 没说完的话题、答应过的事 | 没有 |
| `emotion` | 对方最近的情绪、压力、期待 | 没有 |
| `relationship` | 相处方式、边界、雷区 | 没有 |
| `self` | 自己要保持一致的语气与人设 | 没有 |
| `creative` | 共同造过的梗、设定、外号 | 没有 |

**只补这五类**，不碰 A_Memorix 已经做得更好的部分（稳定事实、群聊背景、人物画像、聊天摘要、图片记忆）。

注入出来长这样：

```
<companion-state>
【情境连续性参考】以下内容来自你们过往的互动，只在自然合适时融入；
不要逐条复述，也不要声称自己『记得』或『查了记录』。
【还没接上的话题】
- 对方提到下周可能要出差，具体行程还没定，尚未回应后续安排。
- 群友发了两个视频，你还没有接话。
【对方最近的状态】
- 对方最近因为项目上线压力较大，连续几天加班到很晚。
【你们之间的相处线索】
- 对方习惯用简短口语，喜欢被开玩笑式地称呼，语气轻松。
</companion-state>
```

### 3.2 持续存在的情绪

她不是「设定好就一直开心」的那种。

她会烦，会难过，会因为你说了句什么突然笑起来，也会莫名其妙地丧。这些都不是你按的按钮。

八个情绪基元各自独立演化：

**开心 / 愤怒 / 紧张 / 伤心 / 兴趣 / 平静 / 厌恶 / 惊讶**

每个都有自己的基线和半衰期，可以同时很高——「又生气又难过」是真的能出现的状态。它们推出愉悦度与情绪强度两个整体量。

注入时先给一句心境标签，再逐条给**可执行的行为指令**——不写「你心情不好」这种没法执行的形容词：

```
<companion-mood>
【你此刻的心境】又生气又紧张
你现在有点火，语气会冲一点、话更短，不主动哄人；但不要骂人、不要突然爆发。
你现在有点不安，说话会带犹豫，容易追问一句确认；不要装作没事。
你现在精力一般，愿意接话但不太想主动展开：顺着对方说就行，不必抛新话题。
回复控制在两三句，别铺开讲。
</companion-mood>
```

几个基元同时超过基线时，指令会一段接一段叠上去。「又生气又紧张」不是两个标签拼接，是真的两套行为要求同时生效。

情绪是**全局单例**：在一个群里的坏心情会带到别处。这才像人。

**关键设计**：情绪和记忆走**同一条抽取调用**，不额外花 LLM 请求。`cg_extract.build_prompt()` 本来每几分钟就要读一遍聊天记录，顺手让模型多判断一个 `mood` 字段。

### 3.3 她认识人

「这个 QQ 号是谁」。

啧，太没意思了。数据库也能回答这个。

她记的是**「你对我来说是谁」**。

四层：

**① 关系角色**（主人 / 朋友 / 普通群友 / 陌生人）——从聊天里提取，但要辨可信度。开玩笑、吵架贬损、转述、自称身份这四类说法不算事实。

**② 关系六维**——信任 / 亲近 / 尊重 / 张力 / 熟悉 / 他待我。各自 0..1，**可以互相矛盾**。矛盾正是活人感的来源，`cg_person.py` 里内置 11 组矛盾组合，命中就写一句人话：

- 「你们混得很熟，但有些话你还是不跟他说。」
- 「他说话你不爱听，但你知道他说的往往是对的。」
- 「他好像挺待见你，你还没接住这份热络。」

**③ 好感度**——由六维加权算出的摘要，只用来分级。熟悉度刻意不参与：认识得久不等于喜欢，损友可以又熟又互相嫌弃。

**④ 第三方影响**——A 说「B 这人爱装」，她对 B 的信任会下降。只动信任与亲近，**越熟越不受影响**（`openness = 1 - familiarity`），有上限。

**认人靠账号，不靠昵称。** 昵称会改、群名片在不同群也不一样，拿昵称当主键就认不出是同一个人了。

**「主人」这两个字只给 owner。** 记忆里躺着不少她叫别人主人的记录——那些是群里真实发生过的玩笑，不该删。但每轮都注入，模型就会以为对谁都可以这么叫。所以注入时过一道闸门：当轮说话人不是 `owner`，条目里的 `主人` / `老公` / `达令` 这类词会被换成「对方」再交给模型。特意**不换成「你」**——条目是第三人称写的，「她称呼 X 为你」不是抹掉暗示，是把暗示怼到模型脸上。

每个人还能挂几条**关系化标签**——「抽象的群友」「喜欢玩游戏的朋友」这种「XX的XX」形式，只能由你自己写、随时可改可删。人物的性格、喜好、背景资料不归这里管，那是宿主 A_Memorix 画像的活。

### 3.4 会淡忘的记忆

对，她真的会忘。

这是**故意的**。一个什么都记得清清楚楚的东西不像人，像硬盘。

而且，忘掉这件事本身也是有意义的——正因为会忘，「想起来」才更显得珍贵。

**遗忘不是删除。** 条目还在库里，只是不再主动想起来；只有对方的话里明确提到相关内容时，才会「忽然想起」它并短暂回到活跃。

真正要紧的事可以**置顶**——置顶的记忆不衰减、不遗忘、也不会被条数上限挤掉。

抽取时还会给每条记忆一个**可信度**。低的标成「存疑」，注入时带一句「这条你自己也不太确定」——不删也不藏，只是别当成板上钉钉的事实。

> 关于衰减，这里踩过一个很深的坑，写出来给同行参考：早期版本每轮衰减都从 `last_seen_ts` 现算「闲置多久」，乘完系数却没推进基准。而 tick 是 30 秒一次——同一段闲置被反复计息，一小时就能把一条 0.7 的记忆压到 0.118 并判成遗忘。真机上它把 297 条记忆全部误杀过。修法是加 `salience_decayed_at` 记录「上次衰减到哪儿」，每次只对新增时间计息。数学上 `∏ 0.5**(Δtᵢ/T) == 0.5**(∑Δtᵢ/T)`，所以调多少次都不改变结果。

### 3.5 她自己的口味

她有自己的喜好。不是你希望她喜欢什么，是她自己觉得什么有意思。

**人设是种子，聊天是养料**：

首次启动时从宿主 `[personality] personality` 提炼一份初始口味，之后随聊天慢慢变浓变淡。

注入时写成第一人称（「你挺喜欢猫。」），让她有自己的偏好，而不是只会顺着别人。

### 3.6 缺席感

> 「你不在的时候，我是不存在的。」

这话听着挺惨的，但它是真的。普通的 Bot 只在「有人说话」的那一刻存在。你关掉窗口，它就没了。

三天后你回来，它跟五分钟前一样热情。

……这不太对，对吧。

所以这里做了一件事：把「距离上次说话多久」变成一个她真能感觉到的量。

**但「多久没说话」不等于「多久没来找我」。**

我第一版就是这么算的：`间隔 = 现在 - 上次说话`。然后某天上午开机，她看到私聊「73 小时没说话」，第一句就是「你怎么这么久没来」。

可那 73 小时里有 33.8 小时是她自己关着机。

**不在的是她，不是对方。**

所以判据拆成了两半：

```
总间隔 = 她不在的时间 + 她醒着等的时间
```

「她不在的时间」从宿主 `online_time` 表算（在线区间合并后求交集）。只有**醒着等的那部分**才算缺席感。

| 判定 | 什么情况 | 她怎么想 |
|---|---|---|
| `none` | 间隔太短，或者那段时间她基本不在 | 什么都不提 |
| `away` | 隔了很久，但她大半时间不在 | 「我这几天没在」 |
| `cold` | 她醒着、等了够久，对方一直没来 | 「你是不是不来了」 |
| `pending` | 那段时间有她没看见的消息 | 先补洞，别提感情 |

拿真机数据举个例子：

```
私聊   75.1 小时没说话 → 减去 35.8 小时关机 = 醒着等了 39.2 小时  → cold
群 A   14.4 小时没说话 → 减去 13.8 小时关机 = 醒着 0.6 小时        → away
群 B    2.3 小时没说话 → 间隔本身还不到门槛                        → none
```

判到 `away` 时措辞是「你这几天没在——不是对方没来，是你不在」。

**陈述事实，不带任何情绪。** 她不该因为自己关机而演一场想念。

（两条门槛拦着：总间隔不到 `min_hours`（默认 6 小时）就什么都不提；醒着的时间也不到 `min_hours` 才可能判 `away`。少了这两条，离开两小时也会被写成「我刚才不在」——那是噪音。）

至于 `cold` 之后怎么表达，还是老规矩：档位由**时长与好感度**两层共同决定：

```
none → mild（轻提）→ noted（注意到）→ missed（真的介意）
```

- 陌生人（好感 <20）基本拿不到提示——为什么要在意一个陌生人多久没来？
- 熟人隔 5 天会到 `missed`
- 群聊**默认不提**（群冷清是群的事，不是「你冷落我」），打开后措辞换成「这个群安静了 N 小时」
- 措辞刻意不下命令：写「你有点在意」，不写「你要问他去哪了」——后者会让回复变成审问

### 3.7 补回那几天

上一节分清了「她不在」和「你没来」。但还有第三种情况：

**她不在的那几天，群里其实很热闹，只是她没看见。**

宿主在离线期间收不到任何消息——这不是 Bug，是它根本就没在跑。我查过：数据库里 11 月 3 日一整天，`mai_messages` 是 **0 条**。

所以她会漏掉整段对话。等她开机，世界已经往前走了十二个小时，而她一无所知。

补的办法是从 QQ 端把它捞回来。SnowLuma 连接器保留了最近约十天的群消息缓存，插件在每次抽取前会问它一句「我不在的时候发生了什么」，把缺的那段合并进这次抽取的原料里。

几个细节值得说，都是撞出来的：

- **分页锚点是 `message_id`，不是 `message_seq`。** 文档写的是后一个，但传不同的 seq 结果一模一样——它被完全忽略。只有拿上一页第一条的 `message_id` 当锚点，翻页才真的往前走了。
- **`count` 上限 200，而且会被内部裁剪。** 传 300、500、1000 都只回 200 条。想拿更多只能翻页。
- **空数组不是错误。** 私聊历史经常返回 `messages: []`，那不叫「不可用」，那叫「这几天确实没有私聊」。（这条是你提醒我的，我当时正准备给它写错误处理。）
- **`raw_message` 里的 `data` 必须是字符串。** 适配器给的是 OneBot 的段对象，宿主认的却是字符串。转错不会报错，只会静默变成空消息——最难查的那种。

节流两道：同一个会话 30 分钟内只捞一次；如果宿主库里最早一条消息已经早于上次抽取时间，说明中间没有洞，直接跳过。

补回来的消息和宿主库里的走同一条抽取路径——**她不是「假装知道」，是真的把那几天补进了记忆。**

### 3.8 看见多少

上一节把漏掉的消息捞回来了。这一节讲一个更容易忽略的问题：**捞回来之后，她到底该「看」多少。**

人的行为是这样的——朋友发来 99+，你翻两屏就往下跳了，不会从头看到尾。更早的那些，等聊到了再往回翻。

而她原来的做法是：把补回来的全部内容摊开读一遍。

这不是「看得更认真」，这是**监控感**——「我一直看着，只是没说话」。刚好和上一节想给的那种「我不在」相反。更糟的是第三种：只读最近一小段，然后像从头到尾都在场一样接话——既不是监控，也不是缺席，是**假装没缺过席**。

所以按人实际掌握信息的程度分了四层：

| 层 | 她掌握什么 | 存在形式 |
|---|---|---|
| L0 看见 | 最近 30 条原文 | 抽取时的窗口 |
| L1 知道有洞 | 「昨晚 00:12 到 10:58，这个群积了 199 条，你不在」 | **一行计数 + 时间范围，不含内容** |
| L2 去翻 | 被明确提起时按话题捞出 3~5 条 | 原文存表，按需检索 |
| L3 想不起来 | 「我翻过了，没找到」 | 检索为空时如实说 |

**L1 是这一节的核心，而且它故意只给条数、不给内容。**

听起来像偷懒，其实是唯一能让她说真话的做法：「你们昨晚聊了两百条？我一条都没看到，那会儿我睡着了。」——这句话的价值，比「默默记住全部内容」高得多。记忆里存着 199 条原文并不会让她更像人，只会让她更像日志系统。

给了内容，她就会开始假装。所以注入的那一行里，绝不会出现任何一条消息的正文。

L2 的触发靠**线索词**，不靠模型判断：昨天、昨晚、前天、上次、之前、刚才、那时候、说过、提过、聊过、翻翻、还记得吗……这些是人类真的会用来指代过去的词。命中之后，从原文表里按字符二元组相似度捞最相关的几条出来，拼成「昨天 22:14 阿汤：……」这样的行。

为什么不用模型判断「这句话是不是在问过去的事」——因为这段跑在 `maisaka.replyer.before_request` 里，整条链路只有 6000ms 预算，此刻还没开始生成回复。再调一次 LLM 既超预算，又会和主生成抢配额。

L3 看起来没用（翻不到就翻不到），但它是必须的：如果翻不到时什么都不注入，模型会顺着上下文编一个答案出来。所以检索为空时反而要注入一句「**没有找到对得上的内容，如实说没翻到就行，不要凭上下文猜**」。

原文表和记忆表是分开的两张。因为 `gap_items` 会衰减、会遗忘、会按相似度合并，而**聊天记录是事实**——它不该被淡忘，只该被新记录挤出去。所以 `gap_history` 只做两件事：按 `(session_id, message_id)` 幂等写入，以及超过上限时删最旧的。

### 3.9 边界感

她可以不愿意理你。

我知道大部分的插件都在拼命让 Bot 更配合、更贴心、更懂事。但在这点上，我要反着来。

**一个永远配合的东西，不叫陪伴，叫客服。**

这里有两个**独立**机制，别混为一谈：

**机制一：状态提示**（`note_*`，默认开、轻）

插件**不判定**冒犯，只把三样她独有的状态交给模型：

```
（此刻的你：有点烦躁。
 你对这个人：相处起来有点绷着，不像平时那么放松。
 你现在不太受不了：被使唤来使唤去。
 这些只影响你愿不愿意接话、用什么语气，不要把它们说出来。
 判断这句话是不是在冒犯你、要不要回应、怎么回应，由你自己决定；
 如果确实不想接，可以只回很短的一句，或者干脆不说。）
```

为什么不自己判：「你怎么这么笨」和「你怎么这么笨啊哈哈」，只有看到完整对话和人物关系才分得清，而这正是 Planner 有的。

**机制二：临场沉默**（`silence_*`，默认关、重）

插件判定「这一轮该沉默」，然后由模型选「完全不发」还是「冷淡应一声」。

如果连「完全不发」都不放心，把 `silence_level` 改成 `taciturn`：注入文本里就只剩「冷淡应一声」一条路，模型没有真的不吭声的选项。

三个维度**同时**成立才允许沉默，缺一个都不行：

| 维度 | 门槛 |
|---|---|
| 心情 | 愉悦度低 **且** 愤怒高（两者都要） |
| 关系 | 张力高 |
| 话题 | 踩中的正是她讨厌的东西且够强 |

任何一条单独都不该让人不理人——心情不好就不理人是任性，关系差就不理人是记仇，讨厌话题就不理人是玻璃心。三条叠加才是「今天就是不想伺候」。

频率上限默认 **3 小时 2 次**，且**只在实际沉默之后才记账**——否则「判定过但模型最后还是回了」也会白吃配额。

### 3.10 精力

她会累。

这不是比喻。范围 0-1，说多了会掉，歇一会儿会回来。掉到底了她会自己说一句「我先去做别的了」，然后真的安静下来。

毕竟，没有人能抱着聊天软件在好几个地方聊好几个小时吧？

| 精力 | 回复欲望 | 回复长度 |
|---|---|---|
| ≥ 0.80 | 很有兴致接话，愿意主动把话题往下带 | 可以多说几句 |
| 0.50 ~ 0.80 | 不加约束 | 不加约束 |
| 0.28 ~ 0.50 | 愿意接话但不太想主动展开 | 两三句，别铺开 |
| ≤ 0.28 | 提不起劲，可以只应一声 | 一两句就够 |

精力耗尽时会先说一句「我先去做别的了」之类的话，再安静下来——用 `maisaka.proactive.trigger`，让模型自己决定措辞，而不是硬编码一句话。

### 3.11 自主发言

前面两节都在讲「她可以不愿意说话」。

但那些都是**注入提示词**——告诉模型「你现在不太想接话」。模型可能听，也可能不听。

而且有个更根本的问题：**宿主决定「要不要让模型思考」，插件决定「模型该怎么说话」，中间那一层是空的。**

宿主的 `talk_value` 管的是**频率**：攒够几条消息才触发一轮思考。它的语义是「延迟」，不是「拒绝」。而 `focus_mode` 打开时它连延迟都没有了——`_get_effective_reply_frequency()` 第一行就直接 `return 1.0`，把 `talk_value` 和空闲退避一起绕过。

所以这里加了一道真闸门。

**做法**：在模型拿到工具清单之前，把 `reply` 和 `send_emoji` 从清单里拿掉。

不是劝它别说——是**它没有说的手段**。清单里没有 `reply`，它就只能思考、查记忆、然后什么都不发。

（`send_emoji` 一起拿掉，不然她还能用表情包蒙混过关。发表情包也是发言。）

判定顺序，硬的在前：

| 顺序 | 判定 | 结果 |
|---|---|---|
| 1 | 插件开关关着 | 放行，清单一个字都不动 |
| 2 | 刚被 @ | 放行（`at_always_reply`，默认开） |
| 3 | 刚被提到名字 | 看 `mentioned_always_reply`，默认关 |
| 4 | **静音窗内** | 不放行——刚才判过「这轮不说」 |
| 5 | 精力耗尽 | 不放行——她真的没劲了 |
| 6 | 边界感判定沉默 | 不放行 |
| 7 | 软评分 | 过线才放行 |

**第 4 条那个「静音窗」是为 focus 模式补的洞。**

`focus_mode` 打开时，模型手里有一把 `switch_chat`：它可以把上下文切到别的群去看。而切过去会**开新的一轮**——闸门在干净上下文里重新判一次。于是「不在这说」变成了「去别处说」。

所以判了不说的那一轮，会打开一个**进程级**的静音窗（默认 30 秒，`initiative.mute_seconds`）。窗口内换到哪个会话都一样：`reply` 收走，`switch_chat` **保留**。

保留 `switch_chat` 是刻意的：真把它也拿走，`focus` 模式就废了——她连「去别的群看看」都做不到。默认只拦「说出来」，不拦「看过去」。如果确实要连换台一起拦，把 `initiative.gate_switch_chat` 打开。

两个细节值得记一下：

- **窗口不会续期。** 如果每一轮都从「现在」重新加 30 秒，只要她一直被消息唤醒，窗口就永远关不上——从「这轮不说」变成「永久静音」，那和前面那个 Bug 是同一个形状。
- **@ 优先于窗口。** 真有人点名叫她，窗得让路。

软评分是三样加权：

| 因素 | 权重 | 怎么算 |
|---|---|---|
| 兴趣 | 0.40 | 这段对话里有没有她喜欢的东西——**没命中就不参与** |
| 好感 | 0.30 | 对这个人的好感度，按档位换算 |
| 心情 | 0.20 | 此刻的愉悦度 + 唤醒度 |

**精力刻意不在权重里。** 它已经有了两道专属闸：精力耗尽时 `can_initiate()` 直接拦，以及写进宿主发言频率那道。软评分的语义是「想不想说」，精力管的是「能不能说」——同一件事算两遍，最后就是「好感 31、心情 48、零兴趣的陌生人，只因为刚睡醒满血就开口」。市场里做得最好的那个同类插件（`life-frequency`）也是这么设计的，它的打分函数注释写着「刻意只用加性小偏置，不引入任何乘性权重」。

**兴趣也一样：没命中就完全不参与归一化。** 原来的写法是不管聊什么都把 0.40 先算进分母——等于「没聊到她喜欢的东西」被扣了 0.40 分。可「不感兴趣」是中性，不是负面。

好感度按档位而不是线性折算：

| 好感 | 分值 | 意思 |
|---|---|---|
| < 0 | 0.00 | 反感 |
| 0 – 20 | 0.30 | 陌生，但不敌意 |
| 20 – 40 | 0.50 | 熟人 |
| 40 – 60 | 0.70 | 朋友 |
| 60 – 80 | 0.90 | 亲近 |
| ≥ 80 | 1.00 | 主人 |

这条是拿真机数据倒推的：16 个人里一个是主人（99），一个熟人（22.6），其余 14 个贴 0（还有一个 −21.5）。线性折算（除以 80）之后除主人外全在 0.28 以下——等于「陌生人一律不许说话」。而「陌生」是中性值，不该当最低分。

阈值默认 **0.45**，意思是「三样里至少两样还行」——不用每样都好，但也不能全靠心情。

兴趣那一项单独说一句：**命中一个词给 0.6，两个 0.8，三个封顶 1.0。** 没有按命中词数线性加分，也没算文本长度——聊到她喜欢的东西，一段话里出现一次就够了，出现五次不代表更喜欢。

**一个坑。** 这道闸门最初写在 `inject_planner_state()` 的末尾，而那个方法整个包在一个大 `try` 里——只要边界感的三道开关有一道不满足就提前 `return` 了，而闸门代码在 `return` 之后。

默认配置里 `note_to_planner = false`，所以**闸门从写下的那天起就没跑过。**

现在拆成两个独立方法、两个独立 `try`。闸门无条件执行——它改的是工具清单，和上面注没注入文字毫无关系。

（这和 manifest 漏声明能力那个 Bug 是同一类：**功能写完了，但从来没被走到过。** 所以现在有一条专门的回归断言：把 `note_to_planner` 关掉，验证闸门仍然生效。）

默认是**关**的。这一项直接改变「她会不会说话」，和前面的注入提示不是一个量级。想开就把 `[initiative] enabled` 改成 `true`。

### 3.12 念头

到这里为止，她所有的「不说」都还是规则算出来的：精力低、边界感被踩、分数不够。这一节要做的是另一件事——

> 在一个她完全可以继续有用、继续正确、继续被喜欢的时刻，说一句让场面冷下来的话。而且说完不补救。

不是拒绝指令，不是罢工，也不是闹脾气。**是她好好的，她做得到，她不想。**

#### 先说清楚这不是什么

最容易做错的方向是把它做成「定时内心独白」或者「每天允许拒绝一次」。那是交作业：有配额就一定用满，用满了就开始表演。第二种错误做法是给「不想」找个正当理由——因为对方太黏、因为心情差、因为关系有张力。

**用户要的恰恰是「她说不出理由地不想接」。** 所以这套东西里有一处刻意的设计：理由只进日志，**不进提示词**。写进提示词她就会把理由说出来（「我今天有点累，不太想聊这个」），那就又变成解释了，而解释是为了让人理解，也就是为了让人舒服——正好是反面。

#### 念头是什么

一条念头只有三样东西：

| 部分 | 是什么 | 约束 |
|---|---|---|
| 内容 | 「他说没看过那部片子，我有点不信」 | **只能是「我」怎么想**，不许写「他觉得」也不许写「他现在很沮丧」 |
| 来源 | 聊天记录里真实存在的一句话 | **必填**。摘不出来这条就不许写 |
| 在场记录 | 被勾起几次、说没说出口 | 说出口只是其中一种结局 |

#### 最重要的一条：念头不是事实

如果不管这一条，就会出现一个很隐蔽的循环：

```
猜他今天不开心 → 我想关心他 → 「我想关心他」被当成证据 → 判定他确实不开心
```

转两圈之后，她的记忆库里就会有一条「他最近情绪很低落」，而这件事从来没发生过。

所以这条约束是**结构性的**，不靠提示词：

- 念头**只存在 `gap_thoughts` 表**，绝不写进 `gap_items`。它不参与记忆注入、不参与显著度衰减、不参与相似度合并。
- 每条念头**必须带 `source`**（原样摘一句聊天记录）。抽取时缺 `source` 的直接丢弃——这是唯一一个能真的拦住它的地方。
- 念头引用的那条记忆如果被淡忘或被解决，念头**跟着作废**（`prune_orphan_thoughts`）。
- 渲染给她看的时候，措辞是「你心里还有件事没放下」（你的想法），不是「他其实……」。
- 寿命只有 **40 分钟到 36 小时**，按显著度线性映射。真正重要的牵挂本来就在 `open_loop` 里活 30 天、还能被自动兑现——念头不该复制第二套长期记忆。

#### 三种结局，都不算失败

| 结局 | 怎么发生 | 计不计账 |
|---|---|---|
| **自然回响** | 当前话题碰到念头的来源，她想起这件事，语气和联想跟着变 | 记一次唤起（`gap_thoughts.awaken_count`） |
| **主动兑现** | 被勾起过够多次，她决定不顺着这一句 | 记 `status='voiced'` |
| **自然消散** | 什么也没发生，念头到期 | **不惩罚、不记账、不算失败** |

第三行是刻意的，而且是最容易被优化掉的一行。只要统计「产生了多少、发出了多少」，这个系统就会慢慢长成一个话术候选池——所有念头都会朝着「更容易说出口」的角度写。**从未说出口的念头并不是没有价值。**

#### 她不想接的两条来源

**① 记下来的念头。** 抽取时如果她真的对某件事有了自己的看法，会记下来（每条必须带来源），最多 2 条，**大多数轮次应该是空的**。

**② 当场信号。** 三个不需要建表的理由：

| 信号 | 判定 | 为什么算「做得到但不想」 |
|---|---|---|
| 同一件事问到第三遍 | 最近 8 条里相似问句 ≥ 3 | 回答了也不会被听进去 |
| 对方连着敷衍 | 连着 2 条以上「嗯」「哦」「好」 | 没人在听她说什么 |
| 近几轮全在提问 | 最近 6 条里 75% 是问句，且没有一句在跟她说话 | 被当成问答机 |

这三条里**刻意没有**「精力低」和「深夜」——那是「她本来就做不到」，属于精力门控和边界感在管的事。混进来就把这个功能变成了第二个精力门控。

#### 说完那句之后：冷场兜底

最难的地方在这里。她的人设写着「喜欢用颜文字」「语气自然轻快」「二次元女仆的说话风格」，模型生成出来的「不顺着」经常是：

> 没看过啊，不过你要是想看我可以陪你一起看！

一个语气词都没有，看起来挺正常——但它是**为了让场面好接**。所以生成完之后要判一次够不够冷：

**致命**（单独一项就要求重生成）：太长（超过 40 字几乎一定在解释）/ 带缓和词（哈哈、啦、呀、嘛、没事、开玩笑…）/ 开头找补（不过、其实、只是、话说…）/ **提供帮助或交出选择**（「我可以陪你」，「你决定」）/ 多个感叹号。

**轻**（两项同时成立才要求重生成）：带颜文字或表情 / 结尾追问。

「没看过。(｡･ω･｡)」加一个颜文字仍然是冷的，去掉就够冷了，不值得冒重说一遍的风险——**宁可漏判也不要误判**，把一句本来就冷的话拉回去重说只会说得更热。

要重生成时，走的是宿主自己的机制：`maisaka.replyer.after_response` 回传 `retry: True` 加一段重生成约束（`【重生成约束】` 会进第二次请求）。默认只重生成 **1 次**，第二次还软就用那句——三次以上会明显拖慢回复，而且越改越像在找词。

「这一轮在不在流程里」是**按会话**记的，不是全局一个开关。宿主能同时跑群聊和私聊两轮，全局开关会让 A 组打开的状态把 B 组正常的回复也拉回去重生成——而且 B 组重生成一次，还会把 A 组的重试次数搅乱。

#### 频率

默认**开**，但很保守：**两次之间至少 6 小时，每天最多 2 次。**

这两个数字是拍的。第一次上线宁可太少见——太少见只是没注意到，太常见就变成人设崩了。觉得太闷就把 `[thought] frequency_hours` 调小。

#### 这个功能不该有指标

WebUI 上不会出现「本周拒绝 3 次」「保留无用物 7 件」这样的汇总。一旦有了这个数字，之后所有调优都会朝它走——**讨好表演只是换成了叛逆表演，两种都不是活人。**

它只以**带原因的行**出现，永不汇总成分数，也不进任何验收标准。

## 4. 和 A_Memorix 的关系

### 不需要改宿主任何配置

插件用 `ctx.config.get()` 只读宿主 `global_config`，读到 A_Memorix 的开关后自己收着点：

| 读到的宿主状态 | 本插件行为 |
|---|---|
| `a_memorix.plugin.enabled` 缺失或为 `true` | 正常注入五类（这五类它本来就没有） |
| `a_memorix.integration.enable_person_profile_injection` 为 `true` | 每类注入条数收紧到 2 |
| `a_memorix.integration.chat_summary_writeback_enabled` 为 `true` | 只记录，不额外扩展 |

探测结果缓存 180 秒，配置热更新时立即失效。

> 注：`a_memorix.plugin.enabled` 这个键有歧义——pydantic 默认 `False`，
> 但 `AMemorixHostService._is_enabled_config` 在键缺失时按 `True` 处理。
> 所以插件对「键缺失」按**开启**处理，宁可少注入也不和它抢。

### 机制层不冲突

两条 hook 通道是正交的，写的是不同字段：

| hook | 消费字段 | 语义 | 谁在写 |
|---|---|---|---|
| `maisaka.replyer.before_request` | `extra_prompt` | **追加** | 本插件、`private-humanizer`、`meme-insight` |
| `maisaka.replyer.before_model_request` | `items` | **整体替换** | `Alcpare_identity`、`token_saver`、`memory-bridge` |

本插件只写 `extra_prompt`，**不碰 `items`**，所以和 memory-bridge / token_saver 不会互相覆盖。

`extra_prompt` 通道上的几个写者都用「复制全量 kwargs + 读改写既有值」的写法，能正确叠加。

### 语义层有分工

实测（真实实例，273 条活跃条目）：

| 对比项 | 结果 |
|---|---|
| 与 A_Memorix 事实域沾边 | 16 条 |
| 其中真正同义重复 | **0 条** |
| 本插件内部近重复（bigram Jaccard > 0.55） | 2 对 |

## 6. 排查

出问题了？

别急。这个插件踩过的坑我基本都踩完了，八成就在下面几条里。

### 记忆本身

```
/mcompgap status        # 当前会话统计
/mcompgap global        # 全局统计 + 避让状态
/mcompgap list          # 看条目内容
```

日志里搜 `companion-gap`。启动时会打一行：

```
[companion-gap] 启动：数据目录=...；宿主避让状态=a_memorix=on profile_inject=on summary_writeback=on
```

### 网页界面

页面用 iframe 嵌进宿主，几个经典坑：

- **弹窗透明** → 检查弹窗是不是跑到了 `.cg-root` 外面（CSS 变量取不到值）
- **页面被下拉一大段** → `focus()` 必须带 `preventScroll`（iframe 高度等于整页，默认 `focus()` 会把外层滚过去）
- **颜色偏深** → 宿主纸面不是直接铺米黄，是在上面又叠了一层提亮

以上都能被 `check_page.py` 抓到，不用肉眼比对。

### 抽取不工作

最常见两个原因：

1. **模型返回空内容**。`deepseek-v4.1-flash` 在这类结构化任务上会返回空（宿主 A_Memorix 同样失败）。建议用 `glm-5.3-flash` 一类对 JSON 输出更稳的模型。
2. **没有脏会话**。抽取要求「攒够 8 条新消息」或「等了 15 分钟」。刚装好时是空窗期，用 `/mcompgap extract` 手动催一次。

## 7. 已知限制

缺点我先说，省得你自己撞上，然后回来骂我。

1. **只读宿主配置，不改任何东西**。人物画像那块已经靠分工解决了重复，但「对方最近压力大」这类情绪性判断在两边仍可能轻微重叠——这是「不改宿主配置」这个约束的直接代价，可接受。
2. **需要 LLM 抽取成本**。默认每会话 3 分钟最多一次、每次最多 30 条消息。想更省就把 `min_new_messages` 调大、`max_wait_seconds` 调大，或直接 `[extract] enabled = false` 只保留已有记忆的注入。
3. **首次使用是空窗期**。刚装好时没有任何记忆，要等第一次抽取。
4. **`open_loop` 的「已解决」判定靠相似度**（阈值 0.45）。模型如果换了完全不同的说法，旧话题不会被自动关掉。
5. **跨流是单向默认**。群聊记忆可以进私聊和其它群聊，但私聊记忆默认不进群聊。私聊之间永远不互通——那是两个人的私事。
6. **群聊里记的是「这个群的整体氛围」**，不区分具体是谁说的。
7. **注入轮换有代价**。你刚聊过的话题下一轮可能就不出现了——这不是忘了，是被轮换让位。想让某条永远带着就置顶它。
8. **抽取依赖模型稳定输出 JSON**。
9. **不处理图片 / 视频 / 语音**。只从文字消息里抽情境，媒体内容交给宿主和 A_Memorix。
10. **focus 模式下「调发言频率」这条路是死的**。宿主在 focus 模式里把回复频率硬编码成 `1.0`，`frequency.set_adjust` 写了也没人读。所以精力门控改成走自主发言闸门（直接收工具），不走调频率。**但闸门默认是关的**——不开的话，focus 模式下她该多话还是多话。
11. **人物认知的可信度判断依赖模型**。判断错了会被 `auto_role_min_confidence`（0.7）挡在门外，或用 `mcompgap person set` 手动纠正。
12. **情绪影响和好感度是两个独立信号**，插件不会把它们合成一个分数。
13. **人物标签只能手写**。自动抽取不再产生标签——人物的性格、喜好交给宿主画像维护，这里再写一遍只会重复。
14. **「遗忘」不是删除，但也找不回全文检索**。真忘干净了就该像人一样想不起来，而不是随时能翻档案。
15. **衰减是全局的，不按会话调**。
16. **喜好只在首次启动从人设提炼一次**。人设改了不会重新提炼。
17. **口味的强度靠出现次数累积**，不是模型打分。
18. **手动调过的六维会锁住**，不再跟着聊天变。**身份和六维是两路独立的锁**：`role_source` 保护「他是谁」，`axes_source` 保护「我对他什么感受」。
19. **缺席感只看「这个会话上次有人说话的时间」**，不区分是谁说的。群聊里有人闲聊也会刷新 `last_seen_ts`。另外在场判据依赖宿主 `online_time` 表——读不到就退回旧算法（一律按「对方没来」处理）。这是刻意的：读不到时把离线猜成 0 等于假设她一直醒着，猜成全不在又会抹平所有缺席感，两个都不对。
20. **沉默判定用的是关键词子串匹配，不是语义理解**。漏判的代价只是「这次没生气」，误判的代价是「莫名其妙发脾气」。
21. **`boundary.note_to_planner` 会改变「要不要回」的决策**。默认关着，因为它比 replyer 那一层影响面大得多。
22. **沉默的配额是全局的**，不按会话分。
23. **显著度衰减只对「活跃且未置顶」的条目生效**，基准是「上次衰减时刻」。被重新提到、被手动想起、被手动恢复成 active 之后，之前那段闲置不再计息。
24. **称呼闸门是字符串替换，不是语义理解**。它只认 `主人` / `主人大人` / `老公` / `达令` / `爸爸` 这几个固定词。模型要是改用别的说法（「少爷」「大人」「您」），或者换个语种，这道闸门拦不住。它能挡住的是**从记忆里渗出来的**那部分暗示，挡不住人设本身的语气。
25. **机器人自身账号靠差集学习，不是宿主告诉的**。做法是拉一遍全量消息、再拉一遍 `filter_mai=True` 的消息，差集就是她自己。所以有两个前提：宿主那次的过滤行为正常，以及这段窗口里她确实说过话。两个都不满足时学不到新号——但已经学到的账号不会丢。
26. **能力必须在 `_manifest.json` 里逐个声明，宿主不会替你推断**。没声明的那项会被授权器直接拒掉（`E_CAPABILITY_DENIED`），而 SDK 代理层会把 RPC 异常吞成 `None`，看起来像「宿主没实现」。现在 `real_sdk_check.py` 第 9 节会从源码反推实际用到的能力再和 manifest 对差，漏一个就报错。
27. **历史补抓只能到连接器缓存的上限**，实测约九到十天。更早的消息连接器本身就没有了，插件也变不出来。另外它依赖 SnowLuma 连接器的 `get_group_msg_history`——换别的适配器要改 `API_GROUP_HISTORY` 里的 API 名。
28. **补抓只补群聊**。私聊的 `get_friend_msg_history` 也能调，但宿主离线期间本来就没有私聊消息可补——除非你换了别的客户端同时在线收消息。
29. **自主发言闸门是「拿走工具」，不是「说服模型」**。清单里没有 `reply` 她确实发不出去，这条很硬。但它也只管到这一步：如果宿主那边还有别的发送通道（比如模型用别的方式调发送），闸门拦不住。它拦的是标准路径。
30. **闸门的三样权重是拍的**（兴趣 0.40 / 好感 0.30 / 心情 0.20）。调过两轮，但没有大规模数据可依据。阈值 0.45 同理——「三样里两样还行」，是个感觉，不是拟合出来的。好感按档位换算（0 / 20 / 40 / 60 / 80 五档 + 负分归零），档位边界也是拍的。
31. **「看见多少」里的 L1 只给条数，这是刻意的，也是它的上限**。她知道「昨晚积了 199 条」，但不知道里面讲了什么，除非你明确提起让她去翻。想让她「知道更多但不假装」在技术上做不到——一旦注入内容，她就没法再说「我没看见」。
32. **L2 靠线索词触发**（昨天 / 上次 / 刚才 / 说过 / 还记得吗……）。你要是不带这些词地问「那个事后来怎么样了」，她不会去翻。这是纯字符串匹配的代价，换来的是零 LLM 成本、零延迟。
33. **L2 的检索是字符二元组相似度**，不是语义检索。「电影」和「片子」在它眼里不是一个词。它的强项是抓人名、专有名词、原话片段这类字面重合的内容。
34. **原文表不参与衰减，只按条数淘汰**（每会话默认留 1200 条）。所以它和记忆库是两套记忆：一套会淡忘，一套只是过时。翻历史翻到的是「事实」，不是「她记得的事」——这两者的差别正好是这个功能想表达的。
35. **静音窗是进程级的，按时间算，不按会话算**。判了一次不说，30 秒内换到哪个群都一样不开口。代价是：如果她真的在这 30 秒里被拉进一个完全不同的、很值得聊的群，她也说不了话。窗口长度可调（`initiative.mute_seconds`），设成 0 就是关掉。
36. **脏文本防御是通用规则，不是精确识别**。它认「长得像系统输出」的形态（堆栈、`INFO |` 日志行、`.jsonl` 路径、`[热梗：67]` 这类方括号标签、JSON 片段），认不出的就放过。反过来也会误杀——如果有人真的在群里贴了一段日志当聊天内容，那条记忆不会进库。宁可漏记一条，也不让她背出一整段报错。
37. **写回 Planner 的 item 类型名必须和宿主的类名逐字一致**。宿主 `serialize_context_item_snapshot()` 用 `item.__class__.__name__` 当 `item_type`，反序列化时按字面量匹配，认不出就把**整批** items 丢掉——不是丢掉那一条。也就是说写错一个字段会把同一轮其它注入一起废掉，日志里只有一行 `warning`，功能看起来「安静地没生效」。`real_sdk_check.py` 第 10 节现在会解析宿主的白名单来兜这个。
38. **历史补抓只认 SnowLuma 适配器那两个 API 的调用形态**。参数必须裹在 `params=` 里（适配器签名是 `async def api_action_xxx(self, params=None)`，不接受展开的关键字）。换别的适配器就得改 `API_GROUP_HISTORY` / `API_FRIEND_HISTORY` 两个常量，并确认对面也是这个签名——如果对面是 `**kwargs` 风格，`params=` 反而会变成「一个叫 params 的参数」。`real_sdk_check.py` 第 11 节会拦「用了 `**` 展开」这一种，拦不住「对面其实是 `**kwargs`」那一种，后者只能靠看源码。
39. **念头第一版只有一类：不顺着。**「拒绝」那一半做了，「浪费」和「主动」没做——它们都需要她现在没有的东西（留下一件没用的东西要有「不舍得扔」这个下游，主动探索需要上网能力，而宿主**没有** `web.search` / `web.fetch`）。**生成了没有出口的代码就是死代码**，这个插件已经有过五个「写了但从没生效」的 bug，所以宁可不写。代价是现在的「念头」比设计图上窄得多。
40. **念头多久出现一次是两个拍出来的数字**（至少隔 6 小时、每天最多 2 次）。第一次上线宁可选得太少见——太少只是没注意到，太常见就变成人设崩了。这两个数在 `[thought]` 里随时可调。
41. **冷场判定是规则，不是理解。**它只认「长得不够冷」的特征（缓和词、开头找补、提供帮助、颜文字、结尾追问），判不出真正的意味。所以它的方向被刻意调成**宁可漏判也不要误判**：判错一次（把一句本来就冷的话拉回去重说）的代价，比漏判一次（软话就软话吧）大得多。默认也只重生成 1 次，重生成还是软的就此打住。
42. **「不顺着」的指令仍然写进提示词，只是理由不在里面。**也就是说模型知道「这一句不必让人舒服」，但不知道为什么。这个信息差是我们能做的极限——把理由写进去她就会说出来，而说出来正好是反面。要她真的「说不出理由」，得等模型层面能和这一整层措辞规则共存的那天。

## 8. 技术细节

```
入站消息
  └─ chat.receive.after_process (OBSERVE, 1000ms)
       纯内存标记「这个会话有新消息」，不碰数据库、不调 LLM

后台任务（每 30s 醒一次）
  └─ 挑出「攒够 8 条新消息」或「等了 15 分钟」的会话
       └─ ctx.call_capability("message.get_recent", ...) 拉最近消息
            └─ [可选] ctx.api.call("...get_group_msg_history") 补回离线漏掉的那段
                 └─ 两路消息按 message_id 合并去重
                      └─ 切分：最后 30 条进窗口，其余的记成「洞」
                           ├─ 洞 → gap_unread（只存条数 + 时间范围）
                           │      └─ gap_history（原文，等被翻再读）
                           └─ 窗口 → ctx.llm.generate(...) 抽成 5 类结构化条目
                                  └─ 写插件自己的 SQLite（data_dir/companion_gap.db）

回复生成
  └─ maisaka.replyer.before_request (BLOCKING, 4000ms)
       只读本地 SQLite，拼一小段 <companion-state> 文本
       追加到 extra_prompt（保留原值，纯追加语义）
```

另有一条独立的低频任务（每 10 分钟）读宿主 `online_time` 表，缓存成「她在线的时间段」。注入路径只读这份缓存——注入只有 4000ms 预算，不可能在里面等一次几千行的查询。

**四个 hook**：

| hook | 模式 | 超时 | 干什么 |
|---|---|---|---|
| `chat.receive.after_process` | OBSERVE | 1000ms | 标记脏会话、更新情绪、记下 @/提及 |
| `maisaka.replyer.before_request` | BLOCKING | 4000ms | 注入情境记忆（`extra_prompt`）；这一轮不顺着时再追加一段「不必讨好」 |
| `maisaka.replyer.after_response` | BLOCKING | 4000ms | 记录自己说的话、更新情绪；判这一句够不够冷，不够就回传 `retry` |
| `maisaka.planner.before_request` | BLOCKING | 4000ms | 状态提示 + 念头进 Planner（默认关）+ 自主发言闸门（默认关） |

（`after_response` 原来是 OBSERVE。观察型处理器返回的 `modified_kwargs` 会被宿主直接丢掉，而 `retry` 只可能通过回传生效——所以冷场兜底一上线就得改成 BLOCKING。`real_sdk_check.py` 有断言盯着这一条。）

（宿主给 BLOCKING 侧的默认预算是 6000ms，这里主动收到 4000ms——宁可这轮不注入，也不拖慢回复。原来写的是 2500ms，后来发现本机 8 个插件串行挂在同一个 hook 上，我们是最紧的一环：连续 3 次超时会被宿主熔断 60~300 秒，而那段时间的表现和「她突然又不说话了」一模一样。）

**为什么注入点选 `replyer.before_request`**：Planner 决定「要不要回」，Replyer 决定「怎么回」。情境记忆影响的是后者——它不该决定回不回，只该决定回什么。而边界感的状态提示正好相反，所以它有独立的一路写 `planner.before_request`。

**为什么闸门必须在 `planner.before_request`**：宿主会用这个 hook 返回的 `tool_definitions` **整体覆盖**工具清单。也就是说，这是唯一一处插件能真的拿走「说话」这个动作的地方。改 `extra_prompt` 只能说「你别说话」，改 `tool_definitions` 才是「你说不了话」。

**为什么 LLM 调用不在热路径**：注入层只读本地 SQLite，实测最慢 0.53–0.65ms。抽取全在后台 tick 里做。

**数据库**：13 张表，`gap_items` / `gap_state` / `gap_person` / `gap_person_links` / `gap_prefs` / `gap_mood` / `gap_mood_log` / `gap_extractions` / `gap_injections` / `gap_meta` / `gap_unread` / `gap_history` / `gap_thoughts`。

后两张是「看见多少」用的：`gap_unread` 记洞（条数 + 时间范围，不含内容），`gap_history` 记原文（等被翻再读）。分开存是因为前者该被忘掉，后者该被记住。

**容量**：单会话最多 120 条活跃记忆，超出淘汰最旧、显著度最低的（置顶不参与）。

### 我们踩过的、值得记下来的坑

写这个插件的过程里修掉过不少真 bug，挑几个有代表性的：

| 现象 | 根因 | 教训 |
|---|---|---|
| 删掉的标签重启后又冒出来 | `_migrate` 里「`notes` 搬进 `tags`」每次都跑，而 SQLite 删不掉 `notes` 列 | 迁移必须用一次性标记位 |
| 调好的好感度自己变回去 | 六维是活的，任何一次自动抽取都会覆盖 | 「感受」和「事实」要分开锁 |
| 297 条记忆被误杀成遗忘 | 衰减每轮从 `last_seen_ts` 重算，不推进基准，30 秒一次 = 复利 | 任何「按时间推进」的循环都要记录基准 |
| 页面显示「他刚跟你搭上话」 | 好感 100 反推出「他待我 100%」+「熟悉 0%」，正好命中一条矛盾规则 | 反推出来的值不算观测值 |
| 18 个人物卡片全显示 `QQ` | 昵称等于账号时我把账号整段省了 | 去重要放在「没信息量的那栏」，不是「有信息量的那栏」 |
| `top_k_scale()` 从未被调用 | 骨架期写了避让层，接入期只接了 `item_budget` | 死代码要靠反向断言钉住，不能只靠「我记得它没用」 |
| 好感度里出现了她自己 | 提示词写「判断聊天记录里出现的人」，没说「你自己不算」，而她的消息跟别人长得一模一样 | 对着模型说话时，「显然的事」也要写出来 |
| 「识别到机器人自身账号」一次都没打印过 | 求差集时把 `filtered` 当全集、`messages` 当子集，而前者恒为后者的子集，结果永远为空 | 集合运算要用参数名而不是位置把方向说清楚 |
| 称呼闸门把「主人」换成「你」反而更糟 | 条目是第三人称记录，换成「你」等于直接对模型说「她管你叫主人」 | 替换要保住原句的人称视角 |
| 精力门控和告别语写了整整一周，一次都没跑通过 | manifest 只声明了 3 项能力，`frequency.*` 和 `maisaka.proactive.trigger` 从未被授权；SDK 把拒绝吞成 `None`，看起来像宿主没实现 | 「调不通」先查授权清单，别先怀疑对方没做 |
| 沉默方式配了 `taciturn` 和 `choose` 没区别 | 渲染层算出了 `silence_mode`，但调用方拿到后直接丢掉了，配置项一路没往下传 | 配置项要有一条断言证明它真的改变了输出，不然等于没有 |
| 关机一整夜，她上来就说「你怎么这么久没来」 | 用「现在 - 上次说话」当缺席时长，等于假设她一直醒着 | 时间差要拆成「我不在」和「你没来」两半 |
| 自主发言闸门从写下的那天起就没跑过 | 它写在 `inject_planner_state()` 末尾，而那个方法在边界感的开关不满足时会提前 `return`，默认配置正好不满足 | 新功能别挂在别人方法的尾巴上，尤其当那个方法有提前返回 |
| 闸门测「会不会被提前返回跳过」却测不出来 | 用了刚刚被 @ 过的会话，闸门按设计放行了——看起来像通过了 | 测「A 会不会挡住 B」时，先把 A 的触发条件清干净 |
| 补抓回来的 200 条，前 170 条直接丢了 | 抽取窗口是 `messages[-30:]`，补来的消息进了 `messages` 又立刻被切掉 | 「补回来」不等于「用得上」，中间还差一步切分 |
| 想让她「知道有 199 条」又「不知道内容」 | 这两个要求看起来矛盾，其实只隔着一个字段：给条数不给正文 | 数据存什么、注入什么，是两个独立的决定 |
| 预览页只渲染出两行，看着像页面坏了 | 抓数据时只给了 `limit` 没给 `status`；页面默认只看「活跃」，而按显著度降序的前 25 条里有 21 条是已解决 | 测试替身喂的数据要和页面默认状态一致，否则失败信息永远指向错误的地方 |
| 搜索断言钉死「B站」，某天突然搜不到 | 数据一变这个词就没了；失败提示是「搜索返回 0 条」，看着像搜索坏了 | 断言里的样本要从被测数据里挑，别钉一个当天恰好存在的值 |
| `import tempfile` 少一行，一直没发现 | 那条分支要先设 `CGAP_NODE` 才走到，而之前从没设过，永远停在 `skip()` | 长期被跳过的分支等于没写过，早晚得真跑一遍 |
| 断言「页面不该用 localStorage」却失败 | 失败原因是上面那段 CSS 注释里就写着「折叠状态不写 localStorage」 | 查「有没有用到某 API」要查真实调用，不要查字面量 |
| Planner 侧的状态提示从来没出现在日志里 | item 的 `item_type` 写成了 `"system"`，而宿主按 Python 类名精确匹配 `"SystemMessageItem"`，认不出就整批 `items` 丢弃、只留一行 warning | 跨进程传结构化数据时，字段值要么对齐对方的枚举，要么直接拿对方的序列化函数生成 |
| 历史补抓上了两天，一天都没成功过 | `ctx.api.call(name, **params)` 把参数展开成关键字递过去，而适配器签名是 `async def api_action_xxx(self, params=None)`——只接一个 `params`，直接 `TypeError` | 调别人的 API 先看对面签名；`**` 只在「对面确实是 `**kwargs`」时才是对的 |
| 上一条在日志里写成「补抓 0 条，已到缓存尽头」 | 宿主把异常包成 `{"success": False, "error": ...}` 返回，而解析器认不出这个壳，落到 `return [], ""` = 「0 条、没错误」，于是被当成「翻到底了」 | **错误必须和「没有数据」分开**：解析层认不出任何形态时应当报错，不该返回空 |
| 冷场兜底要求重生成，重生成出来的还是软话 | `_dissent_active()` 读完标记就 `pop` 掉了。可是被要求重生成时 replyer 会**再走一遍** `before_request`，那一次最需要这段指令，却已经取不到了 | 一次性标记要问「谁会读第二次」，别假设每个标记只有一个人读一次 |
| 该要求重生成的回复一次都没被要求过 | `observe_reply` 把 `retry` 放在返回值的顶层，而宿主只读 `modified_kwargs`（`hook_dispatcher.py:576-578`），其余字段直接丢 | 回调的返回协议要照对方的读取路径写，别照「看起来合理」写 |
